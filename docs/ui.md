Where do new translations go? Add each new key to exactly one matching area in `lang/en/<area>.json` and `lang/de/<area>.json`. Choose the feature that owns the text; use `common.json` for shared labels. Keep area names identical across locales. Laravel and the frontend load all areas together, and the translation parity test rejects missing or duplicate keys.

Sites (`/sites`) is the landing page after sign-in; `/` and `/dashboard` redirect there. The main navigation lists Sites, Incidents, Upcoming, Clients, Maintenance and Activity. The collapsible Operations group contains Runs, plus System health and Updates & backups for Owners and Admins. Operations starts collapsed unless one of its pages is current. Its late-check count and monitoring-health warning remain visible when collapsed. Settings is in the footer. Runs shows a badge for late checks; Incidents shows the open-incident count. Upcoming has no navigation badge. Search sits below the wordmark in the sidebar. It opens the search palette; Ctrl+K or ⌘K also opens it to find sites and clients, go to any page, switch the theme or log out. Press ? for all keyboard shortcuts: G then a letter goes to a page (for example G then I for Incidents), and C starts the create action of the current list. There is no desktop top bar, breadcrumb row or global client switcher. On mobile, a compact bar contains the menu button, wordmark and search button; the drawer also includes search. Navigation closes the drawer after the destination loads. When the connection is lost or a data refresh fails, a warning strip above the page shows the time of the last received data. A healthy connection shows no strip.

The Sites attention band includes all authorized clients, independently of the table's filters. Sites and Incidents use `filter[client_id]`, Activity uses `client`, and Upcoming and Maintenance use `client_id` as independent list filters. Runs uses `client`. Filters do not change other pages or grant access. Owners and Admins are instance-wide; restricted Members see only assigned clients. Personal API tokens additionally intersect this access with their optional client constraint. A stale session client selection is cleared and has no effect.

Above the Sites table, a state sentence and Needs attention band show at most five sites in Down, Failed, Check error or Warning state, ordered by severity. Rows show the recorded cause and time when available, with an incident link where one exists. An outage appears here, not in a full-width incident banner. When more sites need attention, Show all selects the table's Attention filter and scrolls to it, preserving other table filters. The band itself stays independent of those filters. Pending, paused and maintenance states are not attention rows.

Monitoring infrastructure health is separate from site results. A stopped dispatcher warns that displayed results may be stale; degraded monitoring is not proof that a target is down. With no active checks, Sites warns that paused is not fine and links to paused sites. Monitoring timestamps use relative labels within the user's local day and dates across day boundaries; hover or focus reveals the exact time in their timezone on a 24-hour clock.

Live refreshes buffer additions, removals and reordering in the Sites table and attention band behind the N new changes button. Click it to apply the latest received rows. Existing rows can refresh their status without waiting. Maintenance also buffers changed row content, so a foreign edit or natural state transition does not move a window between the shown state filters until applied. Successful mutations from this browser tab update the opted-in Sites and Maintenance lists directly; they do not require applying that tab's own change. Changing the URL or list scope resets the buffer. The count describes differences from the shown rows, not a durable event log or every intervening change. Signals are refresh hints, not an exactly-once delivery promise.

Attention site links use Inertia navigation. If a top-level page GET fails on the network or a deployed page chunk cannot load, the app tries the intended same-origin destination as a full-page request once per URL within 60 seconds in that browser tab. Another failure is reported instead of looping. Background data refreshes do not navigate away; later signals or visibility polling retry. Disconnected sessions or failed refreshes poll the visible page every 15 seconds; reconnecting or returning to a visible tab also requests a refresh. When the shared coverage flag is false, Sites, Add site and the sidebar warn that no channel hears about outages or failures; Owners and Admins get a link to Settings → Notifications. **Who gets this** on a site, check or incident shows which channels would be told and why.

Upcoming lists observed certificate/domain expiration dates, visible maintenance windows and the next due time of infrequent scheduled tasks. Site-, client- and tag-targeted maintenance uses the same viewer-visible window set as Maintenance; restricted Members cannot see private tag windows. Windows with no effective sites can still appear as 0 sites. The range controls are 30 days, 90 days and All; `/upcoming?days=14` is also supported. All means up to 365 days ahead, including generated recurring maintenance occurrences; the list shows the first 100 chronological dates. Activity lists state changes, not every execution; its Every run link opens Runs. The first successful scheduled-task observation is setup, not a change. Filter Activity by site/client, check type and time range.

Status is always a visible word with its icon through `StatusBadge`, including `OK`. Use `StatusDot` only when it has an accessible label. Pages and components must not render standalone checkmark icons or literal checkmarks as status. The source guard in `tests/Arch/ArchitectureTest.php` covers pages, layouts, and non-stock components, including aliased check-style icons imported from Lucide. The completed-run icon and copied-secret feedback icon are the two non-status exceptions; `monitoring-status.test.tsx` checks the shared badge itself.

The site overview, check and settings headers share Pause/Resume, Run all checks and Maintenance navigation. Maintenance shows its scheduled or active window details only to viewers entitled to see them; a restricted viewer of a tag-scoped window sees “Maintenance active” without its private details. The Sites list keeps Status, Site, Why and Checked visible as the table narrows; it drops response history, uptime and checks before squeezing site names or timestamps, and places the client below the site name when the client column is hidden. When the table itself becomes too narrow, it uses stacked site rows. Checked timestamps use the same local-day relative formatter as the attention band.

Site tabs include enabled checks. Site settings can re-enable stored checks; their direct check pages retain configuration and history while disabled. Site settings uses section dividers and one bottom Discard/Save bar for General and check switches. Personal channels live in Settings → My notifications, the team's in Settings → Notifications and a client's on its Notifications tab. To stop one channel hearing about a site, leave the site out in that channel's sheet. Deletion is a separate confirmed action at the end. Owners and Admins can change site configuration; Members cannot.

Client Notifications and Client Settings are authorized tabs beside Sites and Incidents. It uses the same settings layout for name, short name, contact, language and timezone, with Archive as a separate confirmed action. Client timezone still drives recurring maintenance. Branding and team-access editing are absent here; stored branding remains visible in the client mark, and membership is managed in Settings → Members. Sparse identity saves preserve those stored values and assignments. The client list has no Archived tab, but an archived bookmark shows its state and a link back to active clients.

Owners can invite Admins or Members through `POST /settings/members/invitations`; Admins can invite Members only. Member invitations require client IDs. Invites expire after seven days, may be resent or revoked, and can be accepted once through `/invitations/{token}`. An accepted invite verifies the invited address; the accept form cannot change it. A removed account keeps its history but loses sessions, tokens and live connections. An invite to that address explicitly reactivates it without creating a second account. Only Owners may promote another user to Owner, and the last active Owner cannot be demoted or removed. `GET /settings/members/data` includes the last authenticated request, updated at most once a minute.

`GET /invitations/{token}` returns HTML unless JSON is requested through `Accept: application/json` or `X-Requested-With: XMLHttpRequest`.

Owners and admins can ask the add-site form to check an absolute HTTP(S) URL. `POST /sites/probe` returns the final address/status, server header, verified TLS issuer/expiry if available, and a sitemap URL if found. The probe makes bounded server requests, checks every redirect target against public-address rules, and permits six requests per user each minute. Every failed network check returns `probe_failed` with all observed fields null; it does not disclose DNS, connection, timeout, or private-address classifications. DNS lookups and redirects share the total 12-second probe budget. It does not invent site details. It does not save or start a site.

The add-site form selects recommended checks using the existing address probe. Crawl and Lighthouse are recommended only for public HTML responses, excluding authentication and password-form login pages. Sitemap also requires an existing sitemap at `/sitemap.xml` or a reachable robots.txt `Sitemap:` location. Crawl start-page transport failures display a specific Check error, including TLS verification failures; they are not site Down results. Non-HTML, login and noindex crawl targets display an informational Succeeded summary; an absent sitemap does the same without an incident. Invalid sitemaps and unreachable listed URLs remain failures. Detection does not change existing sites or explicit/imported check choices. An HTTP URL excludes HTTPS-only checks from the new site; changing the URL back to HTTPS restores the previous selection. Omit `checks` when using the API to let the server choose the static eligible defaults without a network probe.

Check detail pages share the site header: Run all checks is its primary action, and Maintenance and Pause site are in the More actions menu. Run check is the check header action. Every check shows its persisted RunBar below the tabs; queued, running and late attempts use their recorded state, and only cancellable runs expose Cancel. There is no separate Schedule card; use the RunBar for execution state and the sidebar Runs page for cross-site attempt history. What we check shows effective defaults as well as saved settings, with secrets masked. Uptime shows response-time ranges, a phase breakdown when measured, the latest attempt duration and retained failure status/issue evidence; response headers and body excerpts are not retained. Certificate detail shows observed attributes, time to expiry and trust. Checks without a dedicated layout use the same contract-based summary and history. No run or observation is inferred when none exists.

Owner and Admin users can edit supported check settings from each check's What we check card or from the Checks section of Site settings, where each check row shows its interval and key settings. Both open the same settings sheet, which saves that check at once; the on/off switches in Site settings are saved with the rest of that form. Saving sends only changed fields through the same server validation as the API and does not reveal stored secrets. Health endpoint editing requires a successful unsaved probe through the public-only outbound seam. The saved settings are probed again before persistence; a concurrent configuration change returns 409 instead of silently merging against a different secret. Probes and saves share a six-per-user-per-minute budget charged before outbound dispatch. Stored credentials can be reused only at the stored URL's exact scheme, host, and port; a new origin requires the secret and each retained credential header to be re-entered before any request is sent.

Check settings on the add-site form use each check's configuration schema. Uptime request headers and form payloads have **Name** and **Value**; expected response headers also have **Condition**, and response body rules have **Path**, **Operator** and **Value**. These rows are saved with those field names.

Uptime check detail includes the 20 most recent recorded runs and, independently, up to 50 failed or errored runs from the last 90 days with safe HTTP status, failure reason, and observed total response time. The latest attempt uses the measured response time when available; older attempts fall back to elapsed run time. The page-level `response_times` rollups supply the 24-hour, 7-day, 30-day, and 90-day response-time charts; no per-minute raw history is shipped. Request headers, body content, and configured secrets are never included in this history.

Certificate detail shows up to 20 accepted observations, including issuer, validity window, and whether the certificate changed from the previous accepted observation. A failed fetch does not replace the last accepted certificate. The first observation has no previous certificate to compare against, so its change state is unknown.

Broken-links and mixed-content detail show up to 50 findings from the latest accepted crawl. The latest run's page, time, resource, discovery and comparison limits appear as recorded facts next to its state and separately from accepted findings and their timestamp. An incomplete latest run does not replace accepted results. Previous-week counts appear only when a comparison snapshot exists.

DNS detail compares accepted and current records and shows up to 20 recorded changes. Owners and admins can accept the current observation as normal after confirmation; this records the actor and queues a recheck. While waiting, the new baseline is marked pending. Truncated records are marked as an incomplete comparison.

Lighthouse detail keeps the last measured scores if a later run fails, with a 90-UTC-day daily score series from recorded rollups. Device is shown only if the run recorded it; older runs have an unknown device. Daily aggregates are not split by device, so changing the configured device can mix historical scores.

Scheduled-task definitions are managed through the API, not a web form. Owners and Admins can create a `checks:write` token at `/settings/api-tokens`; Members need an Owner or Admin for definition changes. The [repository API guide](./api.md) lists the endpoints; `/docs/api` is not an application route. Scheduled-task detail shows at most 50 tasks and up to 1,000 retained results from the past 30 days, with a truncation indicator. Owners and admins see each task's full capability ping URL and can rotate it after confirmation. Members see a mask. Rotating a URL invalidates the old URL immediately and requires updating every schedule that uses it; the new URL also appears in the Heptapod API task response. Rotations are actor-audited, views are not.

Application-health detail keeps the last accepted component states and labels after an HTTP failure. It marks those states stale when a newer attempt exists, reports recent HTTP status and failure reason, caps remote text at 160 characters, and excludes arbitrary remote metadata. Configured secrets are redacted from component text.

DNS detail compares the latest accepted observation with the accepted baseline. The first complete snapshot is accepted automatically. Changed records stay in warning until an owner or admin accepts the snapshot they reviewed. The action posts `accepted_run_id`; if a newer observation exists, it refuses acceptance and asks for review again. Acceptance is audited with the actor and observation run ID. Acceptance queues a fresh DNS run. The current warning remains until that real run confirms recovery; a different new change stays a warning without another change notification. Recovery resets that notification episode, so a later deviation can notify again. While awaiting a valid recheck the page reports acceptance pending. The **Accept changes automatically** setting defaults off; enable it for records that rotate intentionally to use the earlier rolling-baseline behavior. Record comparison ignores TTL, ordering, host case, and trailing dots. Existing baselines remain accepted on upgrade.

The incident list defaults to incidents opened in the last 30 days **and every still-open incident**, even one opened earlier. The CSV export uses the same filter. All time includes older resolved incidents. Its scoped 30-day summary gives incident count, elapsed duration total, and median. Open incidents accrue duration until the current time. `GET /incidents/export` downloads the currently filtered, authorized incident rows as CSV; use the same `filter[...]` parameters as the list. An export above 10,000 rows returns 413 in the active language: narrow the filters. Column headings and incident states are translated. Text that spreadsheet apps could interpret as a formula is escaped. Open and resolved incidents use the same page. An open incident shows what the check sees now; a resolved incident shows only its evidence at close: the stored opening evidence after secret redaction, the recorded recovery, up to 20 retained successful runs since recovery, and the retained results between first failure and close. Its timeline runs from the opening to the recovery. Missing historical retries or evidence are not reconstructed.

A channel's sheet has Pause/Resume. Paused channels show Paused / Pausiert and the row summary starts with "Paused: nothing is sent." The pause acknowledgment reports how many queued notifications were discarded; resuming does not restore them. **Who gets this** lists paused channels under Not sent. Members change only their own channels; the server authorizes every change.

Administrative incident closures show Check disabled, Site paused, Site deleted/marked for deletion, or Site moved to another client in the timeline. Their incident page and Activity say Closed, not Resolved or Recovered, and do not claim a first good result. Re-enabling monitoring starts a fresh failure streak; a subsequent threshold-qualified failure opens a new incident.

Owners and admins can regenerate an alert preview at `GET /incidents/{incident}/alerts/{event}`, where the event belongs to the incident and is an opening, uptime reminder, historical reminder, or recovery event. For an event with an accepted email delivery, this route returns JSON containing the rendered HTML, subject, and selected channel (first accepted email delivery by ID). It regenerates content from the retained event and current rendering code, channel locale/timezone and instance settings without sending an email. It is not the historical HTML that was sent. Delivery-time content and settings are not snapshotted; later edits can change the preview. The preview dialog displays HTML in a sandboxed iframe and does not preview the separately rendered plain-text mail part. Unsent, suppressed, digest-only, or non-email events return 404; no sample notification is fabricated. Team-only incident notes never appear in the mail. The incident timeline groups the email of each opening, reminder and recovery with its delivery outcome; expanding a group lists every delivery. Email of other incident events, such as a missed scheduled task, appears under Other notifications (the latest 50, with a notice when older deliveries are omitted). A preview action appears only on the delivery whose recipient the preview actually renders.

The site header links to the site's filtered maintenance list. An open incident during active maintenance names the window's end, whether it mutes alerts, and links to the site's windows. Maintenance windows display their exact start and end hours in the window's timezone. Daily recurrence intervals count days; monthly series can switch between a day of month and an nth weekday when edited. Only owners and admins can edit or cancel windows or series.

In local and testing environments, `/dev/components` shows the component library and its states. This route is not available in production. Live updates and visible-page polling continue when the healthy-connection badge is hidden; monitoring-health warnings appear in the sidebar.

For local board review, run `docker compose exec app php artisan heptapod:seed-demo` after migrating. It defaults to `--scenario=attention` (24 clients and 64 reserved-domain sites). Select `calm`, `incident`, `empty` (first run: user only), `many-sites` (64 sites, uptime checks only) `maintenance` (calm plus an active maintenance window) or `stopped` (stale dispatcher/scheduler heartbeat, overdue checks) with `--scenario=…`. Use a fresh local database before selecting a different scenario; repeating the same seed does not duplicate sites. `scripts/dev-up.sh` runs the real scheduler and dispatcher in every non-stopped scenario: the local update check is pinned off in the untracked `.env`, a configured instance heartbeat URL is refused, and enabled checks are scheduled 24 hours out so the fixture stays still during a review. Horizon never runs, so no check executes over HTTP. `stopped` starts neither service and keeps its stale heartbeats and overdue checks. Demo login is `test@example.test` / `password` at `/login`; `dev-up` prints this path. The seeder refuses to run outside local/testing; it never contacts the example hosts. The `attention` scenario records four certificates and three domains expiring within 30 days through the real check recorder. The seeder temporarily recognizes `.example` as a demo suffix; production uses the unchanged public suffix list. `calm` has 38 scheduled tasks with timely pings. All scenarios with sites seed one team email channel that hears outages only. `attention` also seeds the review-state sites (client `wp5-review-fixture`) and the check-detail data on `demo-01`. No demo notification is sent to an external address.
